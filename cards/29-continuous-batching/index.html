Continuous Batching：大模型推理真正的“批处理单位”，为什么不是请求，而是一次 token 迭代

Sep 11, 2026
阅读时长: 8 分钟

Continuous Batching：大模型推理真正的“批处理单位”，为什么不是请求，而是一次 token 迭代

主题：Continuous Batching / Iteration-Level Scheduling（连续批处理 / 迭代级调度）
领域：AI 全栈工程 × 大模型推理 × GPU 系统 × 高性能计算
推荐阅读时间：约 8–10 分钟
这期转到 AI 推理基础设施。Continuous Batching 值得学，因为它揭示了 LLM serving 和普通神经网络 inference 的一个根本区别：

\[\boxed{ \text{LLM 请求不是一次 forward pass，而是一串长度未知的 forward passes。} }\]

如果还沿用传统“收集一批请求 → 整批跑完 → 再接下一批”的 batching 思路，会造成非常严重的 GPU 空转。

2022 年 OSDI 的 Orca 把调度粒度从 request level 降到 iteration level：每生成一轮 token 后，已经完成的请求立即退出，新请求立即加入。论文在其 GPT-3 175B 实验中报告，相同延迟水平下相比 FasterTransformer 可达到最高约 36.9× 的吞吐提升。今天 Hugging Face Transformers、vLLM、SGLang 等推理体系都采用或建立在类似 continuous batching 思路之上。

真正值得理解的不是“动态加请求”这句话，而是：

\[\boxed{ \text{调度器开始控制 token，而不只是控制 request。} }\]

1. 为什么普通 static batching 在 LLM 上特别浪费？

传统图像模型一次请求可能就是：

\[x\rightarrow f_\theta(x)\rightarrow y.\]

所以四个请求组成 batch：

\[[x_1,x_2,x_3,x_4]\]

一起 forward 一次，然后全部结束。

LLM 完全不同。

一个请求可能生成：

\[8\]

个 token，

另一个：

\[500\]

个 token，

第三个：

\[2000.\]

自回归生成意味着：

\[x_{t+1} = f_\theta(x_{\le t}).\]

所以每生成一个新 token，都要再次执行模型。

假设一个 batch：

1
2
3
4

A:  20 tokens
B: 200 tokens
C: 500 tokens
D:  50 tokens

如果采用传统 request-level batching，运行到：

\[t=20\]

以后 A 已经结束。

batch 实际变成：

1
2
3
4

A: empty
B: active
C: active
D: active

到 \(t=50\)：

1
2
3
4

A: empty
B: active
C: active
D: empty

最终 GPU 实际上在等 C。

问题可以概括为：

\[\boxed{ \text{batch occupancy 随生成过程不断下降。} }\]

而刚结束的槽位却不能立即给排队的新请求使用。

Orca 论文正是针对这种 generative workload 的 multi-iteration 特性提出 iteration-level scheduling。

2. Continuous Batching 的核心操作其实非常简单

假设 GPU 最大允许：

\[B_{\max}=4.\]

初始：

1
2
3

iteration 1

[A][B][C][D]

若第二轮之后 B 生成 EOS：

1
2
3

iteration 2

[A][ ][C][D]

调度器立即从等待队列拿 E：

1
2
3

iteration 3

[A][E][C][D]

再过几轮 A 和 D 完成：

1

[A done][E][C][D done]

马上加入：

1

[F][E][C][G]

因此 batch 不再是一个固定对象。

它变成：

\[\boxed{ B_t= \{\text{第 }t\text{ 次迭代被调度的活跃 sequences}\} }\]

并且：

\[B_t\neq B_{t+1}.\]

Hugging Face 当前 ContinuousBatchingManager 的行为就是每轮检查已完成请求，并立即用队列中的请求补充 GPU 容量。

3. 为什么“一次 token iteration”才是自然的调度单位？

因为 autoregressive decode 的最小同步计算单位就是：

\[\boxed{\text{每个活跃 sequence 生成一个 token}}\]

。

假设当前有：

\[B\]

个 sequence。

一次 decode iteration：

\[\{x_1,\ldots,x_B\} \rightarrow \{t_1,\ldots,t_B\}.\]

GPU 并不特别关心：

  • sequence 1 是三分钟前进来的；
  • sequence 2 是刚进来的；
  • sequence 3 还剩 500 token。

只要它们当前都需要：

\[\boxed{\text{执行下一次 forward}}\]

就可以组成计算 batch。

所以 Orca 的关键变化并不是：

batching 更聪明了。

而是重新定义：

\[\boxed{ \text{scheduler 的工作单位。} }\]

传统：

\[\text{request}\]

Orca：

\[\boxed{\text{iteration}}\]

。

这是一个很典型的系统设计原则：

调度粒度应该匹配工作负载真正可以被抢占和重组的粒度。

4. 但问题随即出现：不同 sequence 的长度根本不一样

假设：

\[A\]

已经生成到 1000 token，

而：

\[B\]

才 50 token。

Attention 对 A 需要读取：

\[KV_A[1:1000],\]

对 B 读取：

\[KV_B[1:50].\]

因此不像普通 GEMM 那样简单：

\[X\in\mathbb R^{B\times d}\]

就可以全部整齐打包。

早期 Orca 为此提出 selective batching：

  • 对线性层等天然适合 batch 的操作一起执行；
  • 对依赖各 sequence 不同历史长度的 attention 部分进行更有针对性的处理。

这也是为什么 Orca 不只是“写一个队列”——真正困难的是让变长 sequence 在 Transformer execution engine 里能够高效共存。

5. 这正好解释了 PagedAttention 为什么后来如此重要

前面知识卡片讲过 PagedAttention。

Continuous Batching 解决：

\[\boxed{\text{谁什么时候进入 GPU 计算}}\]

PagedAttention 解决：

\[\boxed{\text{这些不断加入/退出的请求，其 KV Cache 放在哪里}}\]

。

Continuous batching 会让：

  • sequence 动态加入；
  • sequence 随时结束；
  • 每个 sequence 长度不断增长；
  • KV cache 生命周期完全不同。

如果 KV cache 必须连续分配：

\[[---------A---------] [---B---] [--------------C--------------]\]

那么动态换入换出请求很容易产生：

  • fragmentation；
  • over-allocation；
  • batch size 受限。

vLLM 的 PagedAttention 把 KV cache 做成类似虚拟内存页的 fixed-size blocks，并报告其系统相较 Orca 等基线在相同延迟下可得到约 2–4× 的吞吐提升。

所以两者的关系可以非常清楚地写成：

\[\boxed{ \text{Continuous Batching = computation scheduling} }\]\[\boxed{ \text{PagedAttention = state-memory virtualization} }\]

。

二者共同组成现代 LLM serving 的基础。

6. Continuous Batching 真正困难的地方，在 Prefill 和 Decode 混在了一起

查看完整推导与细节

一个 LLM 请求有两个性质完全不同的阶段。

Prefill

输入：

\[L_p\]

个 prompt tokens。

整个 prompt 可以并行处理。

因此有大量矩阵计算：

\[\boxed{\text{compute intensive}}\]

GPU 利用率很高。

它直接影响：

\[\boxed{\text{TTFT — Time To First Token}}\]

。

Decode

每次只增加：

\[1\]

个 token。

需要反复读取 KV cache。

单个 request 的计算规模相对小，常更偏 memory-bandwidth bound。

它影响：

\[\boxed{\text{ITL/TBT — Inter-Token Latency}}\]

。

Sarathi 的工作明确指出，这两种 phase 的计算特征非常不同：prefill 很容易把 GPU 算力吃满，而单次 decode 的计算利用率相对较低，因此 decode 特别依赖 batching。

7. 一个长 Prefill 可以把所有正在聊天的人“卡住”

假设 GPU 当前正在给 32 个用户 decode：

1

D D D D D D D D ...

每次 iteration 比较短。

突然进来一个：

\[10000\text{-token prompt}.\]

如果直接把整个 prefill 一次做完：

1

████████████████████████ long prefill

那么原先 32 个 decode 请求可能在这段时间完全得不到执行。

用户看到的就是：

1
2
3
4

模型正在输出……
突然停住
……
又继续输出

即：

\[\boxed{\text{inter-token latency spike}}\]

。

所以“continuous batching”并不自动等于低延迟。

你还必须决定：

\[\boxed{ \text{prefill 与 decode 如何共享 GPU 时间} }\]

。

这就是现代 LLM scheduler 的真正核心。

8. Chunked Prefill：把一个大任务切碎，让 decode 穿插进去

Sarathi 提出的关键方法之一是：

\[\boxed{\text{chunked prefill}}\]

。

例如原 prompt：

\[8192\text{ tokens}\]

不要一次运行：

\[8192,\]

而拆成：

\[1024+1024+\cdots+1024.\]

于是执行可以从：

1
2
3
4

Prefill(8192)
Decode
Decode
Decode

变成：

1
2
3
4

PrefillChunk(1024) + decodes
PrefillChunk(1024) + decodes
PrefillChunk(1024) + decodes
...

Sarathi 称其中一种策略为：

\[\boxed{\text{decode-maximal batching}}\]

——尽量保留大量 decode，再用 prefill chunk 填充 GPU 的计算能力。

其论文实验报告，例如 LLaMA-13B/A6000 条件下 decode throughput 最高提升约 10×，端到端吞吐最高提升约 1.33×；后来的 Sarathi-Serve 进一步针对真实 serving 中 throughput-latency tradeoff 优化调度。

9. 为什么 Chunked Prefill 这么巧？

查看完整推导与细节

因为 prefill 和 decode 正好存在互补性。

Decode：

\[\boxed{\text{单请求计算量小}}\]

所以需要很大的 batch 才能充分利用 GPU。

Prefill：

\[\boxed{\text{单请求计算密度高}}\]

很容易利用 GPU。

因此可以把它们混合：

\[\boxed{ \text{prefill 提供 compute intensity} + \text{decode 提供并发 token workload} }\]

。

这是一种很典型的：

\[\boxed{\text{heterogeneous workload co-scheduling}}\]

。

它与简单的 FIFO 队列已经是完全不同层级的问题。

10. 所以现代 scheduler 更像一个“token budget 分配器”

传统 batch size：

\[B=32.\]

但 LLM 中一个 request 在当前 iteration 可能需要：

  • decode：1 个新 token；
  • prefill：2048 个 prompt tokens；
  • chunked prefill：512 个 tokens。

因此只限制：

\[\text{number of sequences}\]

并不能很好描述一次 GPU workload。

现代 scheduler 更自然的约束是：

\[\boxed{ \sum_i n_i^{(\text{scheduled})} \le T_{\max} }\]

其中：

\[T_{\max}\]

是一次 iteration 的 token budget。

Hugging Face 当前 Continuous Batching 配置已经直接暴露类似的 max_batch_tokens 概念，并让 scheduler 根据 token budget、KV-cache blocks 和请求状态选择每轮执行内容。

这意味着 batching 已经从：

\[\boxed{\text{“这一批有多少请求？”}}\]

进化成：

\[\boxed{\text{“这一轮 GPU 应该处理多少 token，以及属于哪些请求？”}}\]

。

11. 为什么只看 tokens/s 会误判 serving 系统？

查看完整推导与细节

假设系统 A：

\[10000\text{ tokens/s}\]

系统 B：

\[8000\text{ tokens/s}.\]

看起来 A 更好。

但如果：

A

TTFT：

\[4\text{s}\]

inter-token latency：

\[150\text{ms}\]

B

TTFT：

\[0.5\text{s}\]

inter-token latency：

\[35\text{ms}\]

对于交互式聊天：

\[\boxed{B\text{ 很可能明显更好。}}\]

因此 LLM serving 通常至少要同时观察：

\[\boxed{\text{Throughput}}\]\[\boxed{\text{TTFT}}\]\[\boxed{\text{ITL/TBT}}\]

以及尾延迟：

\[P_{95},P_{99}.\]

Sarathi-Serve 的研究重点正是：最大吞吐与低延迟之间并非自然一致，需要显式设计 scheduling policy。

12. Continuous Batching 其实引入了一个排队论问题

查看完整推导与细节

设请求到达率：

\[\lambda.\]

服务能力：

\[\mu.\]

当：

\[\lambda\ll\mu,\]

系统很空。

这时为了拼大 batch 等待更多请求反而会增加：

\[\boxed{\text{queueing delay}}\]

。

但当：

\[\lambda\rightarrow\mu,\]

batching 会显著提高 GPU efficiency。

所以 scheduler 一直在权衡：

\[\boxed{ \text{等一等，凑更大的 batch} }\]

和：

\[\boxed{ \text{立即执行，降低当前用户 latency} }\]

。

这和离线 benchmark 完全不同。

离线：

\[\boxed{\text{永远有任务可算}}\]

在线：

\[\boxed{\text{任务随机到达，而且用户正在等}}\]

。

所以 AI serving 本质上已经进入：

\[\boxed{ \text{queueing + scheduling + memory management} }\]

系统工程领域。

13. Continuous Batching 和 CUDA Graph 又存在天然冲突

查看完整推导与细节

GPU 喜欢固定形状：

\[B=32,\quad L=128.\]

这样可以：

  • kernel fusion；
  • CUDA Graph capture；
  • 提前优化内存；
  • 减少 launch overhead。

Continuous batching 却天然制造动态形状：

\[B_t= 31,32,29,32,\ldots\]

sequence lengths：

\[L_i\]

也各不相同。

因此现代 inference engine 经常会把动态 workload 映射到有限的：

\[\boxed{\text{shape buckets}}\]

或 graph sizes。

Hugging Face 当前 continuous batching 配置也包含 CUDA graph、padding intervals、KV-cache block 等硬件相关配置。

这是非常典型的系统矛盾：

\[\boxed{ \text{scheduler 希望动态} }\]

而：

\[\boxed{ \text{GPU kernel 希望静态} }\]

。

高性能 serving engine 的工作，就是在这两者之间建立中间层。

14. 一个容易忽视的问题：公平性

查看完整推导与细节

假设队列中有：

请求 A

prompt：

\[100\]

tokens，

预计生成：

\[50.\]

请求 B

prompt：

\[100000\]

tokens。

如果 scheduler 一直优先 decode：

\[A\]

体验很好，

但 B 的 prefill 可能一直排不上。

反过来，如果一到长 prompt 就立即完整 prefill：

\[B\]

又会严重阻塞正在 decode 的请求。

所以 scheduler 还需要处理：

\[\boxed{\text{starvation / fairness}}\]

。

真实系统因此可能引入：

  • FCFS；
  • priority；
  • token budget；
  • chunk limits；
  • preemption；
  • aging；
  • latency SLO aware scheduling。

这说明 continuous batching 并不是一个单独算法，而是：

\[\boxed{\text{一个 scheduler architecture}}\]

。

15. 为什么 reasoning model 会让这个问题更严重？

查看完整推导与细节

传统聊天可能输出：

\[100\sim500\]

tokens。

推理模型可能输出：

\[5000, 10000,\]

甚至更多。

于是某些请求长期占据：

\[\boxed{\text{KV cache + decode slot}}\]

。

这会同时影响：

  • memory occupancy；
  • concurrency；
  • queue length；
  • tail latency。

因此 2026 年仍有大量研究继续围绕 reasoning workload 的：

  • KV compression；
  • scheduling；
  • high concurrency；

展开。例如 2026 年的 Zipage 就直接把 reasoning 长输出引起的 KV-cache concurrency 限制作为核心 serving 问题。

也就是说 Continuous Batching 并没有“解决完” LLM serving。

它只是建立了现代调度的基本框架。

Agent 请求并不像普通 chat request。

它可能：

    ↓

也就是说 request 会出现：

\[\boxed{\text{暂停—恢复}}\]

。

如果暂停期间仍把完整 KV cache 长期占在 GPU 上：

\[\boxed{\text{昂贵显存会被闲置状态占满。}}\]

\[\boxed{\text{Agent runtime infrastructure}}\]

很好的入口。

19. 它给其他工程领域一个很强的迁移启发：重新寻找“最小可调度工作单元”

Continuous Batching 最深的地方其实并不限于 LLM。

原来系统认为一个不可分割任务是：

\[\boxed{\text{request}}\]

Orca 发现真正可以安全重组的是：

\[\boxed{\text{iteration}}\]

。

这是一种很强的系统优化方法：

当 workload 不均衡时，先检查当前 scheduling granularity 是否太粗。

例如物理求解器里：

  • 一个 frame；
  • 一个 body；
  • 一个 island；
  • 一个 constraint batch；
  • 一个 Newton iteration；
  • 一个 element kernel；

哪个才是真正合适的工作单位？

有时性能问题不是 kernel 太慢，

而是：

\[\boxed{\text{scheduler 根本看不到足够细的可重组工作。}}\]

20. 这和 GPU 物理引擎甚至有一个很直接的类比

假设有 100 个 physics islands。

传统方式：

1
2
3

batch 16 islands
等最慢 island 完成全部 solver iterations
再换下一批

如果不同岛所需迭代数差异很大：

\[4,\ 5,\ 30,\ 100,\ldots\]

就会遇到类似 static batching 的问题。

另一种思路：

\[\boxed{ \text{以 solver iteration 为粒度重新装填 active islands} }\]

。

已经收敛的 island 退出，

新 island 加入。

虽然具体 GPU 数据布局会复杂很多，但思维与 Orca 几乎一致：

\[\boxed{ \text{variable-length iterative workloads 需要 iteration-aware scheduling。} }\]

这就是这张卡片对物理求解器最值得迁移的一点。

今天值得留下的一句话

Continuous Batching 最值得记住的不是：

“请求完成以后立即补一个新请求。”

真正重要的是：

\[\boxed{ \text{生成式模型的自然调度单位不是 request， 而是一次生成迭代。} }\]

知识体系可以这样定位：

\[\text{Autoregressive inference}\]\[\downarrow\]\[\boxed{\text{Iteration-level / Continuous Batching}}\]\[\downarrow\]\[\text{Paged KV memory} + \text{Prefill/Decode scheduling}\]\[\downarrow\]\[\text{high-throughput LLM serving}.\]

而一旦真正进入生产系统，还要继续解决：

\[\boxed{ \text{吞吐} \leftrightarrow \text{TTFT} \leftrightarrow \text{inter-token latency} \leftrightarrow \text{fairness} }\]

之间的多目标权衡。

所以 Continuous Batching 的地位有点类似操作系统中的进程调度：它自身不改变模型任何一个权重，却可能让同一块 GPU 的有效服务能力相差数倍乃至更多。

这也是 AI 全栈工程里一个很值得长期保留的视角：

\[\boxed{ \text{模型性能决定“一个请求能做到什么”； 调度系统决定“同一份硬件同时能为多少人做到”。} }\]

查看扩展内容

  1. Yu et al., Orca: A Distributed Serving System for Transformer-Based Generative Models, OSDI 2022。continuous/iteration-level batching 的奠基工作。重点看 iteration-level scheduling 与 selective batching，而不只是性能数字。
    Orca 作者/团队论文页

  2. Kwon et al., Efficient Memory Management for Large Language Model Serving with PagedAttention, SOSP 2023。理解 continuous batching 下一步为什么必然撞上 KV-memory 管理问题；vLLM 把 paging 与动态 batching 组合成现代 LLM serving 基础架构。
    vLLM / PagedAttention 论文

  3. Agrawal et al., SARATHI: Efficient LLM Inference by Piggybacking Decodes with Chunked Prefills。非常推荐继续阅读，核心是为什么 prefill 和 decode 性质差异巨大，以及 chunked prefill 如何利用这种互补。
    SARATHI 论文

  4. Agrawal et al., Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve, OSDI 2024。从“continuous batching 能跑”进一步进入“生产系统如何同时控制 throughput、TTFT 与 decode latency”。
    Sarathi-Serve 论文

  5. Hugging Face Transformers — Continuous Batching 官方文档。截至当前版本已经直接提供 ContinuousBatchingManager、token budget、PagedAttention、CUDA Graph、chunked prefill 等完整机制，很适合把论文概念对应到真实 API 与 scheduler。
    Transformers Continuous Batching
