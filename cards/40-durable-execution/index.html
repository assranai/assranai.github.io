Durable Execution：工业 Agent 如何正确处理“执行了一半”

Oct 04, 2026
阅读时长: 1 分钟

主题：Durable Execution（持久化执行）与幂等性设计
领域：Agent 工业应用 × 分布式系统 × AI 全栈工程
阅读时间：约 4–5 分钟
关键词：Event History、Replay、Idempotency、Exactly-once Effect

本期转向此前覆盖较少的 Agent 工业应用。

一个工业 Agent 可能需要连续运行数小时：检索文献、调用仿真软件、处理结果、写入数据库，最后生成报告。

问题在于，Agent 的某一步执行成功，并不意味着系统知道它已经成功。

假设 Agent 向仿真服务器提交了一个耗时两小时的任务。服务器已经接受任务，但 Agent 在收到确认前因网络中断而崩溃。

重启后，它应该重新提交，还是等待原任务？

这个看似简单的问题，实际上涉及分布式系统中最重要的一类可靠性问题：如何在无法确定上一次操作是否成功的情况下安全恢复执行。

Temporal 等工作流系统的核心设计，正是围绕持久化事件历史、故障恢复和可靠重试展开的。

一、为什么简单保存 Agent 状态还不够？

假设工作流为：

\[ A\rightarrow B\rightarrow C \]

其中：

  • \(A\)：生成仿真输入；
  • \(B\)：向服务器提交仿真；
  • \(C\)：下载结果。

Agent 在完成 \(B\) 后，需要保存：

\[ \text{state}=\text{B completed}. \]

但可能发生以下事件：

\[ \underbrace{\text{服务器接受任务}}_{t_1} \rightarrow \underbrace{\text{Agent 崩溃}}_{t_2} \rightarrow \underbrace{\text{状态写入数据库}}_{t_3} \]

由于：

\[ t_2状态数据库仍然认为：

\[ B=\text{未完成}. \]

如果 Agent 直接重试 \(B\)，就可能产生两个仿真任务。

这里存在一个重要的分布式系统事实：

外部操作的执行与本地状态的保存，通常无法天然组成一个原子事务。

因此，单纯增加 checkpoint 并不能彻底解决问题。

二、Durable Execution 如何恢复执行？

持久化执行通常将工作流拆分为两类操作：

Workflow： 决定下一步做什么。

Activity： 真正执行外部操作，例如调用 API、写入文件或启动仿真。

Workflow 的执行过程被记录为 Event History：

\[ H=\{e_1,e_2,\ldots,e_n\}. \]

例如：

\[ e_1=\text{WorkflowStarted} \]\[ e_2=\text{ActivityScheduled}(B) \]\[ e_3=\text{ActivityCompleted}(B,r_B) \]

其中 \(r_B\) 是 Activity 的返回结果。

当 Worker 崩溃并重启时，系统可以通过 Replay（重放） 恢复工作流状态。

如果历史已经记录：

\[ \text{ActivityCompleted}(B,r_B), \]

重放时直接使用：

\[ r_B \]

继续执行，不必再次运行 \(B\)。

Temporal 官方文档明确指出，Workflow 恢复依赖持久化 Event History；已经完成的 Activity 在重放期间返回历史结果，而不会重新执行。

但有一个关键限制：

如果外部操作已经成功，而 Activity 的完成事件尚未被持久化，Activity 仍可能被重新执行。

因此，还需要第二个机制。

三、Idempotency：让重复执行不会产生重复效果

查看代码与实现

幂等性的数学定义非常简洁：

\[ \boxed{f(f(x))=f(x)} \]

在工程系统中，可以理解为：

\[ \boxed{\text{同一个逻辑请求重复执行，不应产生额外业务效果。}} \]

例如：

submit_simulation(
    task_id="case_001",
    parameters=...
)

第一次调用：

1

case_001 → 创建任务 → 返回 job_872

第二次调用：

1

case_001 → 发现任务已存在 → 返回 job_872

因此，即使 Agent 重试十次，仍然只有一个逻辑仿真任务。

这种设计通常通过 Idempotency Key（幂等键） 实现。

例如：

\[ k= \operatorname{Hash}( \text{workflow\_id}, \text{step\_id}, \text{input\_version} ). \]

服务端保存：

\[ k\rightarrow(\text{request hash},\text{job id},\text{status}). \]

同一个 \(k\) 对应相同请求时返回既有结果；如果同一个 \(k\) 对应不同参数，则拒绝请求。

Amazon Web Services 的工程实践特别强调：重试本身并不危险，危险的是重试可能产生新的副作用。通过幂等请求标识与参数一致性检查，可以显著简化客户端的故障恢复逻辑。

需要注意，幂等键必须由真正执行副作用的服务端原子地检查和登记。如果只是 Agent 在内存中检查任务是否存在，仍然可能出现并发重复提交。

四、真正重要的区分：At-least-once 与 Exactly-once Effect

查看扩展内容

分布式系统经常使用三种执行语义：

语义 含义 主要风险
At-most-once 最多执行一次 失败后可能丢失任务
At-least-once 至少执行一次 可能重复执行
Exactly-once effect 业务效果恰好发生一次 需要额外去重与一致性机制

对于工业 Agent，常见的合理选择是：

\[ \boxed{ \text{At-least-once execution} + \text{Idempotency} \Rightarrow \text{Exactly-once effect} } \]

这里的箭头表示一种需要满足严格条件才能实现的工程设计目标，并非无条件的数学保证。

例如，仿真服务必须保证同一个任务键只创建一个任务，任务结果也必须能够被重复查询。

如果底层工具不支持幂等提交，工作流框架本身无法保证外部副作用恰好发生一次。

这也是为什么工业 Agent 的可靠性最终会深入到 API、数据库和任务调度器层面。

def simulation_activity(case):
    key = stable_hash(case.id, case.version)

    job = scheduler.find_by_key(key)

    if job is None:
        job = scheduler.submit(
            case,
            idempotency_key=key
        )

    result = scheduler.wait(job.id)

    return {
        "job_id": job.id,
        "result_hash": hash_file(result),
        "result_path": result
    }

这段代码隐含一个重要前提：scheduler.submit() 必须支持服务端幂等处理，或者任务登记与提交具有等效的一致性保障。单纯的 find_by_key() 再 submit() 不能防止并发竞争。

随后由持久化工作流记录：

\[ \text{ActivityCompleted} \]

及其返回结果。

这样即使发生：

  • Agent 进程崩溃；
  • LLM API 超时；
  • 仿真运行两小时后网络中断；
  • 数据处理阶段异常；

系统也可以根据持久化历史与外部任务标识恢复进度。

如果涉及多个数据库或消息队列，还可以进一步引入 Transactional Outbox，解决数据库状态更新与事件发布之间的双写一致性问题。AWS 的官方架构指南提供了相应实现。

六、为什么这对 LLM Agent 尤其重要？

传统工作流通常具有确定性：

\[ s_{t+1}=F(s_t,a_t). \]

但 LLM Agent 可能包含：

\[ a_t=\pi_\theta(s_t,\xi_t), \]

其中 \(\xi_t\) 表示采样等随机因素。

如果恢复执行时重新调用 LLM：

\[ a_t'\neq a_t \]

完全可能发生。

因此，工业 Agent 需要区分两类行为：

决策结果可以记录和重放。 已经生成并确认的计划、工具参数、人工审批结果，应作为持久化数据保存。

外部操作必须能够安全重试。 文件写入、数据库更新、任务提交等，应通过幂等键、唯一约束或外部状态核对处理。

LangGraph 的持久化机制使用 checkpointer 保存工作流状态，并支持中断恢复与 human-in-the-loop。其官方文档也特别提醒：内存型 checkpointer 无法跨进程重启保存数据，生产环境应使用持久化存储。

这里还存在一个容易忽略的问题：代码升级可能破坏重放的一致性。 如果旧工作流记录的是执行 A 后执行 B，而新版本代码改成执行 A 后执行 C，就需要工作流版本管理或迁移机制。

七、局限与工程代价

Durable Execution 解决的是执行可靠性，并不能保证 Agent 的决策正确。

即使一个工作流可以完美恢复，它仍然可能稳定地执行一个错误的仿真方案。

此外，持久化机制还会引入：

  • 事件历史与检查点的存储开销；
  • 工作流版本兼容问题；
  • 外部任务状态与本地记录的对账成本；
  • 不可逆操作的补偿处理；
  • 长期运行任务的资源回收问题。

因此，可靠工业 Agent 还需要权限控制、结果验证、人工审批和审计机制。

它在整个知识体系中卡在哪里？

Agent 工程可以粗略分成四层：

\[ \boxed{\text{Reasoning}} \]

决定做什么。

\[ \downarrow \]\[ \boxed{\text{Planning / Tool Use}} \]

决定怎样调用工具。

\[ \downarrow \]\[ \boxed{\text{Durable Execution}} \]

保证任务在故障、重试和中断后能够正确推进。

\[ \downarrow \]\[ \boxed{\text{External Systems}} \]

真正执行仿真、数据库操作、文件处理和工程任务。

前三层中，LLM 研究通常最关注 Reasoning 和 Planning。

但从工业落地角度看，Durable Execution 是 Agent 从交互式助手走向长期自主运行系统时必须补齐的基础设施。

它的价值在于把一个模糊的问题：

Agent 失败以后怎么办？

转化为一组可以明确设计和验证的工程契约：

\[ \boxed{ \text{可恢复状态} + \text{确定性重放} + \text{安全重试} + \text{外部副作用一致性} } \]

今天最值得记住的一句话：

工业 Agent 的可靠性，不取决于它永远不失败，而取决于它能否在失败发生后，准确判断哪些事情已经完成、哪些事情可以重试，以及哪些事情绝不能重复。
